# Аналитическая платформа банковских данных

**Автор:** Мазориев У.А.

Данный проект является собственной разработкой автора и посвящен созданию аналитической платформы для обработки, хранения и визуализации банковских данных. Основная идея проекта заключается в том, чтобы показать, как на базе доступных open-source и отечественных решений можно построить полноценный контур работы с данными: от операционной базы-источника до аналитической витрины и интерактивного BI-дашборда.

Проект имитирует работу банковской информационной системы, в которой ежедневно появляются сведения о клиентах, счетах, транзакциях, филиалах, банковских продуктах, контрагентах, категориях операций и курсах валют. Эти данные проходят несколько этапов обработки: сначала сохраняются в операционном контуре, затем выгружаются в объектное хранилище, после этого загружаются в хранилище данных, приводятся к согласованной структуре, превращаются в аналитическую витрину и становятся доступными для визуального анализа.

## Общее описание проекта

Аналитическая платформа предназначена для демонстрации полного жизненного цикла данных в организации, работающей с большим количеством транзакционной информации. В качестве предметной области выбрана банковская деятельность, поскольку для нее характерны регулярные операции, множество связанных сущностей, требования к качеству данных и необходимость оперативной аналитики.

В проекте рассматривается типовая задача: у организации есть операционная система, где фиксируются ежедневные действия клиентов, но для аналитики такие данные напрямую использовать неудобно. Операционная база ориентирована на запись и обслуживание бизнес-процессов, а не на построение отчетности. Поэтому данные необходимо выделить в отдельный аналитический контур, очистить, структурировать, связать между собой и подготовить для быстрого построения отчетов.

Разработанная платформа решает эту задачу за счет построения многоуровневой архитектуры. Каждый слой выполняет отдельную роль: операционный слой хранит исходные данные, объектное хранилище используется как промежуточная зона файлового обмена, слой Staging принимает данные почти в исходном виде, слой Core формирует согласованную модель, слой DM предоставляет витрины для анализа, а ClickHouse и DataLens обеспечивают быстрый доступ к итоговой аналитике.

## Актуальность проекта

Современные организации накапливают большие объемы данных, но сами по себе эти данные не дают управленческой пользы без правильной обработки и представления. Особенно это заметно в банковской сфере, где каждый день формируются транзакции, изменяются остатки по счетам, используются разные валюты, появляются новые клиенты и продукты. Для принятия решений важно не просто хранить эти сведения, а быстро получать из них понятные показатели.

Актуальность проекта связана с несколькими факторами:

- ростом объема данных, которые требуется регулярно обрабатывать;
- необходимостью отделять аналитическую нагрузку от операционных систем;
- потребностью в прозрачной архитектуре, где понятно происхождение каждого показателя;
- интересом организаций к open-source-инструментам и импортонезависимым решениям;
- востребованностью BI-аналитики для мониторинга финансовых и клиентских показателей;
- необходимостью автоматизировать регулярные процессы загрузки, преобразования и публикации данных.

Проект показывает, что аналитическую платформу можно построить без использования закрытых коммерческих экосистем, применяя распространенные инструменты, которые можно развернуть локально и адаптировать под конкретные требования.

## Цель проекта

Цель проекта — спроектировать и реализовать аналитическую платформу банковских данных, которая обеспечивает автоматизированную загрузку, хранение, обработку и визуализацию информации с использованием open-source и отечественных технологических решений.

Для достижения этой цели в проекте реализованы следующие задачи:

- смоделирована операционная база банковских данных;
- разработана структура хранилища данных с несколькими логическими слоями;
- организована выгрузка данных в объектное хранилище;
- настроены процессы автоматической загрузки и преобразования данных;
- создана аналитическая витрина для отчетности;
- выполнена загрузка итоговой витрины в ClickHouse;
- подготовлена возможность визуализации данных в Yandex DataLens;
- оформлены SQL-скрипты, DAG-процессы и Docker-конфигурации для воспроизводимого запуска проекта.

## Преимущества проекта

Ключевое преимущество проекта — комплексность. В нем реализована не только база данных или отдельный дашборд, а связанная аналитическая инфраструктура, где каждый компонент выполняет понятную функцию.

Основные преимущества:

- **Использование доступных технологий.** Платформа построена на open-source и отечественных решениях, что снижает зависимость от закрытых коммерческих продуктов.
- **Модульная архитектура.** Каждый слой можно развивать отдельно: источник данных, файловое хранилище, DWH, аналитическая витрина, ClickHouse и BI-инструмент.
- **Автоматизация процессов.** Загрузка и преобразование данных выполняются через DAG-процессы Airflow, что делает обработку регулярной и управляемой.
- **Разделение операционного и аналитического контуров.** Операционная база не перегружается аналитическими запросами, а отчетность строится на специально подготовленных структурах.
- **Поддержка масштабирования.** Использование ClickHouse для финальной витрины позволяет работать с большими объемами данных и ускорять аналитические запросы.
- **Воспроизводимость.** Проект разворачивается через Docker Compose, поэтому его можно запускать в локальной среде без сложной ручной настройки.
- **Наглядность результата.** Итоговые данные доступны для анализа в BI-инструменте, что делает результат понятным не только техническим специалистам, но и пользователям, работающим с отчетностью.

## Общая схема движения данных

Платформа демонстрирует полный цикл обработки данных:

```text
OLTP PostgreSQL -> MinIO -> Staging PostgreSQL -> Core PostgreSQL -> DM PostgreSQL -> ClickHouse -> DataLens
```

Основная идея проекта заключается в разделении операционного, промежуточного, аналитического и визуального контуров. Операционная база имитирует банковскую систему-источник, MinIO используется как S3-совместимое объектное хранилище, PostgreSQL DWH хранит слои Staging/Core/DM, ClickHouse выполняет роль высокопроизводительного слоя витрин, а Yandex DataLens используется для построения аналитического дашборда.

## Основные контуры системы

### Операционный контур

Операционный контур реализован в PostgreSQL и имитирует банковскую систему-источник. В нем создаются таблицы клиентов, счетов, транзакций, филиалов, валют, категорий, контрагентов и банковских продуктов.

Основной SQL-файл:

```text
sql_scripts\ddl_sid_tables.sql
```

Также в проекте есть файл:

```text
sql_scripts\test_oltp.sql
```

Он содержит близкую структуру OLTP-таблиц и может использоваться для тестового создания операционного слоя.

### Объектное хранилище

MinIO используется как S3-совместимое хранилище для исходных файлов. В него выгружаются:

- справочники в виде snapshot-файлов;
- транзакционные данные с партиционированием по дате;
- курсы валют из внешнего источника.

Основной бакет:

```text
bank-analytics-lake
```

Пример логической структуры бакета:

```text
raw/
├── cbr/
│   └── rates_YYYY-MM-DD.csv
├── dicts/
│   └── <table_name>/snapshot_YYYY-MM-DD.parquet
└── not_dict/
    └── transactions/YYYY/MM/YYYY-MM-DD.parquet
```

### DWH-контур

DWH-контур реализован в PostgreSQL и включает несколько логических слоев.

| Слой | Назначение | SQL-файл |
|---|---|---|
| Staging | Первичная загрузка данных из файлов | `sql_scripts\ddl_staging.sql` |
| Core | Очищенные и согласованные данные с ключами и связями | `sql_scripts\ddl_core.sql` |
| DM | Представление для отчетности | `sql_scripts\ddl_datamarts.sql` |

В Staging-слое таблицы повторяют структуру источника и оптимизированы под массовую загрузку. В Core-слое используются первичные ключи, внешние ключи и индексы. В DM-слое создается представление `v_transactions_reporting`, объединяющее транзакции, клиентов, счета, филиалы, категории, контрагентов и курсы валют.

### Аналитический контур

ClickHouse используется как аналитическая СУБД для хранения финальной витрины:

```text
learn_db.f_transaction_details
```

SQL-файл создания витрины:

```text
sql_scripts\clickhouse_dm.sql
```

Витрина создается на движке `MergeTree`, партиционируется по месяцу транзакции и сортируется по дате и идентификатору транзакции. Она используется как источник данных для Yandex DataLens.

Общая последовательность обработки:

```text

        v

        |

        |
        v

        |

```

Параллельно с генерацией и переносом операционных данных выполняется загрузка курсов валют:

```text
load_cb_courses -> MinIO -> staging.exchange_rates -> core.exchange_rates
```

## Описание DAG-процессов

### `generate_oltp_data_daily`

Файл:

```text
docker\airflow_docker\dags\generate_data_to_sid.py
```

DAG имитирует ежедневную работу банковской системы. Он создает новых клиентов, счета, связи клиентов с продуктами и транзакции.

Особенности:

- используется библиотека `Faker` с русской локализацией;
- данные создаются по логической дате Airflow `ds`;
- перед повторной генерацией удаляются транзакции за целевую дату;
- массовая загрузка выполняется через PostgreSQL `COPY`;
- DAG настроен с `catchup=True`, поэтому при первом запуске может начать создавать данные с даты `2025-01-01`.

### `load_cb_courses`

Файл:

```text
docker\airflow_docker\dags\load_cb_courses.py
```

DAG загружает курсы валют USD, EUR и CNY из XML-сервиса Банка России.

Этапы:

1. Формирует запрос к сервису Банка России по дате Airflow `ds`.
2. Парсит XML-ответ.
3. Сохраняет результат в MinIO в формате CSV.
4. Загружает данные в `staging.exchange_rates`.

### `oltp_s3_dwh`

Файл:

```text
docker\airflow_docker\dags\oltp_s3_dwh.py
```

DAG переносит данные из операционной базы PostgreSQL в MinIO и затем в Staging-слой DWH.

Особенности:

- справочники выгружаются snapshot-файлами;
- транзакции выгружаются с партиционированием по году и месяцу;
- основной формат файлов — Parquet;
- при повторном запуске срез данных за дату предварительно очищается;
- используется `ExternalTaskSensor`, ожидающий завершения генерации данных.

### `staging_to_core`

Файл:

```text
docker\airflow_docker\dags\staging_to_core.py
```

DAG переносит данные из Staging-слоя в Core-слой.

Особенности:

- используется `S3KeySensor` для проверки наличия файлов в MinIO;
- загрузка организована по группам зависимостей через `TaskGroup`;
- для справочников используется `ON CONFLICT DO UPDATE`;
- транзакции загружаются после клиентов, счетов и справочников;
- предусмотрена обработка ошибок через callback.

### `postgre_to_ch`

Файл:

```text
docker\airflow_docker\dags\postgre_to_ch.py
```

DAG обновляет аналитическую витрину ClickHouse.

Особенности:

- ожидает завершения `staging_to_core`;
- перед загрузкой очищает таблицу `learn_db.f_transaction_details`;
- загружает данные из PostgreSQL-представления `v_transactions_reporting`;
- использует table function `postgresql()` на стороне ClickHouse.

## Запуск основного контура

Перед запуском необходимо создать внешнюю Docker-сеть, так как оба compose-файла используют сеть `bi-network`.

```powershell
docker network create bi-network
```

Если сеть уже существует, Docker сообщит об этом. Это не является ошибкой.

Запуск основного контура:

```powershell
cd D:\VKR\docker\airflow_docker
docker compose up -d
```

Проверка контейнеров:

```powershell
docker compose ps
```

Остановка:

```powershell
docker compose down
```

Остановка с удалением volumes, то есть с потерей данных:

```powershell
docker compose down -v
```

Использовать `down -v` следует только если нужно полностью пересоздать окружение.

```text

raw/dicts/<table_name>/snapshot_YYYY-MM-DD.parquet
raw/not_dict/transactions/YYYY/MM/YYYY-MM-DD.parquet
```

### Проверка PostgreSQL DWH

Проверить наличие данных в слоях Staging и Core можно через SQL-запросы:

```sql
select count(*) from staging.transactions;
select count(*) from core.transactions;
select count(*) from core.exchange_rates;
```

Проверка DM-представления:

```sql
select *
from dm.v_transactions_reporting
limit 10;
```

Если представление создавалось без явного указания схемы, может использоваться:

```sql
select *
from v_transactions_reporting
limit 10;
```

```sql
select count(*)
```

```sql
select *
```

## Типовые проблемы

### Сеть `bi-network` не найдена

Создать сеть:

```powershell
docker network create bi-network
```

### Airflow не видит DAG

Проверить, что DAG-файлы лежат в каталоге:

```text
docker\airflow_docker\dags
```

И что этот каталог смонтирован в контейнер:

```text
./dags:/opt/airflow/dags
```

### DAG не запускается из-за подключения PostgreSQL

Проверить connections в Airflow:

- `postgres_oltp`;
- `postgres_dwh`;
- `minio_conn_id`;
- `clickhouse_default`.

### В MinIO нет файлов

Проверить DAG:

```text
oltp_s3_dwh
```

и бакет:

```text
bank-analytics-lake
```

### В ClickHouse пустая витрина

Проверить:

1. Выполнился ли DAG `staging_to_core`.
2. Есть ли данные в `v_transactions_reporting`.
3. Выполнился ли DAG `postgre_to_ch`.
4. Создана ли таблица `learn_db.f_transaction_details`.

### DataLens не подключается к ClickHouse

Проверить:

- доступность ClickHouse по `http://clickhouse:8123` внутри Docker-сети;
- наличие общей сети `bi-network`;
- корректность логина `username` и пароля `password`;
- наличие базы `learn_db`.
